# 1.0.7 已播放线路的缓冲与回退修正

## 已确认原因

1.0.6只屏蔽 frequent_buffering；continuous_buffering 达12秒仍会主动停止当前播放器。RecoveryPolicy只向后遍历候选，全部用完就 EXHAUSTED，不记忆本次选台中曾经出过首帧的来源。因此仍会出现能播放的线路被放弃、最后停成黑屏。

## 本次修正

- 当前来源在本次选台中出过首帧后，普通连续缓冲不再触发应用层停止/换源，交给Media3继续加载。短暂反复缓冲同样不切源。
- 明确播放错误仍恢复，避免将已经进入错误状态的播放器一直留在原地。
- 备源用完后，回到最近出过首帧的来源，等待至少30秒（默认60秒）再重连；不再把它终止为“本轮重试结束”。这不是认定它仍然有效，而是保留自动恢复机会。
- 从未出过画面的全部失败来源仍保持有限重试；用户换台/退出通过原有会话标识取消旧重连任务。
- 保留缓冲下载速度，并在缓冲日志记录内核是否加载、播放速度、声明视频码率、缓存和直播窗口，便于区分等待新分片与下载赶不上播放。声明码率不等于实测码率。

## 成熟内核机制核查

Media3会提前下载已发布分片，不需要应用每秒重新prepare。它的DefaultLoadControl在直播中会把开播/恢复阈值限制为目标直播延迟的一半；所以配置20–45秒缓冲上限，并不代表实际已经缓存20秒。短直播窗口也不可能凭空提供45秒未播放内容。

直播速度控制会在缓冲后增加目标延迟，允许稍微放慢以积攒余量。这些是内核已有能力，本次未在缺乏电视实测证据时改写该算法，也未加入多分片并发下载。

## 验证边界

新增策略测试先复现“返回EXHAUSTED而非曾播放来源”，修正后验证回退和延迟。电视模拟器测试直接触发连续缓冲恢复入口，断言仍在原线路、单播放器且没有终止。模拟器不能证明TCL电视在移动宽带上的连续播放质量；一秒一缓冲的初始原因仍需下载/缓存/窗口数据验证。
