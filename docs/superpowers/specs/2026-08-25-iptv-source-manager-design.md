# IPTV 播放源管理工具设计说明

## 1. 项目目标

本项目使用 Python 开发一套开源 IPTV 播放源管理工具。系统自动发现公开可访问的播放源，检测真实播放能力，只保留高速、稳定、高清的频道线路，并生成电视播放器可以直接订阅的标准 M3U 文件。第一版既可在本地运行，也可完全依托 GitHub Actions 定时执行，并通过轻量 GitHub Pages 页面展示检测结果。

系统不破解服务、不绕过认证、不生成受保护的动态签名、不转发或转码视频，也不保存节目内容。公开可访问不等于已经获得再分发授权，因此发布结果必须区分官方源与社区发现源，并保留来源记录，便于审核和移除。

项目设计文档、实施计划、README、配置注释及用户可见页面统一使用中文；Python 标识符使用英文。

## 2. 已确认需求

- 每天从配置好的公开网页和 GitHub 种子地址发现播放源。
- 每周通过 GitHub API 搜索新的公开 M3U/M3U8 列表。
- 第一版支持 HTTP/HTTPS HLS、HTTP MPEG-TS 直链和兼容的 HTTP FLV 流。
- 为 RTMP/RTSP 预留接口，但第一版不发布这些协议。
- 第一版不支持 UDP/RTP/SRT、P2P 或依赖专用插件的协议。
- 使用两级检测：异步 HTTP 初筛，再由 `ffprobe` 验证真实媒体流。
- 线路选择优先级为：稳定性、启动速度、清晰度、码率。
- 每个源保留最近 30 次检测结果。
- 分别发布官方、社区、综合推荐和备用线路订阅。
- 频道分类为央视、地方频道、香港、台湾；地方频道只保留主流省级卫视。
- 不抓取、不保存、不展示频道 Logo。
- 某次任务失败或结果不完整时，必须保留上一版有效订阅。

## 3. 总体架构

项目采用文件化流水线。职责明确的 Python 模块通过统一数据模型和带版本的 JSON 文件衔接，由 GitHub Actions 调度，GitHub Pages 读取最终状态 JSON。第一版不依赖数据库或持续运行的后端服务。

```text
配置种子 / GitHub API 搜索
            ↓
        发现并下载
            ↓
     解析、标准化、去重
            ↓
       异步 HTTP 初筛
            ↓
       ffprobe 媒体复检
            ↓
    频道识别、分类、聚合
            ↓
    滚动历史与质量评分
            ↓
     发布策略与主备选择
            ↓
 M3U 输出 + 状态 JSON + Pages
```

## 4. 播放源发现与发布边界

`sources.yml` 配置种子 URL、来源类型、启用状态和抓取限制。每日任务抓取种子；每周任务通过 GitHub Actions 自带的 `GITHUB_TOKEN` 调用 GitHub API，并限制搜索词、文件大小、请求次数和允许协议。

新 URL 只能先进入隔离候选池，不得直接发布。抓取器不得登录第三方服务、使用 Cookie 解锁内容、推导临时签名或抓取登录墙后的资源。

每个候选源记录来源地址、首次发现时间、来源类型和最近检测时间：

- `official`：电视台、政府、公共机构发布，或明确允许公开播放的源。
- `community`：从社区列表或 GitHub 搜索发现的公开源；项目不宣称其已经获得再分发许可。

状态页清楚标注来源层级和来源地址。维护者可通过配置禁用来源或 URL。

## 5. 数据模型

每条播放源保存：稳定的 `stream_id`、标准 `channel_id`、标准名称、来源中的原名、分类、标准化 URL、来源地址、来源类型、协议、首次发现时间、最近检测时间、最近成功时间、生命周期状态、最近 30 次检测摘要和当前评分。

生命周期状态为：`candidate`（候选）、`active`（主用）、`backup`（备用）、`cooling`（冷却）和 `retired`（退休）。代码内部使用英文枚举，中文页面显示对应中文名称。

单条检测摘要包含检测时间、成功状态、失败代码、首字节时间、启动时间、持续传输指标、分辨率、视频与音频编码、可获得的码率和连续读取结果，不包含媒体内容。

## 6. 检测流水线

### 6.1 HTTP 初筛

使用 `httpx.AsyncClient`，同时限制全局并发和单域名并发。检测 DNS 与连接、状态码与重定向、内容类型或内容特征、首字节延迟，以及能否读取少量有效数据。对于 HLS，解析主播放列表，选择可用变体，并验证媒体播放列表和至少一个分片。登录页、HTML 错误页、空响应、不支持协议和重定向循环直接判定失败。

### 6.2 媒体复检

HTTP 初筛通过后，才以受限并发子进程运行 `ffprobe`。流必须包含视频轨道；程序读取分辨率、帧率、编码、码率和音频信息，并验证约 8 秒的持续出流能力。所有子进程均有严格超时和输出大小限制。

### 6.3 发布硬门槛

- HTTP 初筛和 `ffprobe` 复检都成功。
- GitHub Actions 节点测得的首字节时间不超过 5 秒。
- 媒体至少持续可读 8 秒。
- 默认最低分辨率为 720p。
- 某频道没有合格高清源时，可在频道配置中单独允许降级至 540p。
- 新源至少连续两次定时检测成功后才能发布。
- 地址不需要绕过认证、携带 Cookie 或生成受保护的签名。

状态页必须说明延迟和速度来自 GitHub Actions 节点，并非用户本地网络实测值。

## 7. 频道标准化与分类

`channels.yml` 是显式频道白名单。每个频道配置稳定 ID、标准名称、分类、可识别别名及可选的单频道质量例外。完全匹配或规范化别名匹配可以自动识别频道；无法可靠识别或存在歧义的名称进入运行报告，不得直接发布。

- `央视`：白名单内的 CCTV 频道。
- `地方频道`：只包含主流省级卫视，不包含市级或县级频道。
- `香港`：少量知名香港频道。
- `台湾`：维护一份台湾知名频道白名单。

项目不抓取、不保存、不输出 `tvg-logo`，网页也不显示图片。

## 8. 评分与线路选择

评分基于最近 30 次检测：

```text
总分 = 可用率 × 40
     + 启动速度 × 25
     + 清晰度与码率 × 20
     + 连续读取稳定性 × 15
```

各子项先归一化至 0～1，再乘以权重。启动速度不超过 1 秒为 100 分，1～2 秒为 85 分，2～3 秒为 70 分，3～5 秒为 50 分，超过 5 秒不具备发布资格。分辨率基础分为：2160p 100 分、1080p 90 分、720p 70 分、540p 45 分；低于 540p 默认不发布。分辨率与码率明显不匹配或反复卡顿时降低质量分。

同一频道最多发布一个主源和两个合格备用源。健康主源只有在备用源高出至少 8 分且连续两次检测更优时才被替换；主源失败时可立即切换至合格备用源，以避免偶发波动造成频繁换源。

## 9. 生命周期与定时清理

- 第一次失败：保留主源，记录失败并降低近期评分。
- 连续失败两次：线路进入冷却状态，并提升合格备用源。
- 连续失败三次：从公开订阅移除。
- 冷却源降低检测频率，恢复后重新参与候选排序。
- 连续失败 30 天：候选源退休，但保留精简指纹，避免立即重复抓回。
- 每个源只保留最近 30 条检测摘要。
- 原始来源列表暂时不可用时，不立即删除其中仍可播放的源；发布策略仍可独立禁用它。

## 10. 发布文件

- `official.m3u`：每频道一个最佳官方源。
- `community.m3u`：每频道一个最佳社区源。
- `combined.m3u`：每频道一个推荐源，合格情况下优先官方源。
- `backup.m3u`：主源和最多两个合格备用源，备用线路名称带线路后缀。
- `status.json`：静态网页使用的精简数据。
- `report.json`：运行统计、淘汰原因、失败原因和未识别频道名称。

M3U 条目包含 `tvg-id`、`tvg-name`、`group-title` 和频道名称，不包含 `tvg-logo`。生成的 M3U 和 JSON 必须非空并通过语法或结构校验后才可替换现有文件；任务部分失败或超时时保留上一版有效文件。

## 11. 静态状态页

GitHub Pages 使用原生 HTML、CSS 和少量 JavaScript，不引入大型框架。页面只加载 `status.json`，不加载图片，并将外部文本作为纯文本安全渲染。

页面展示有效频道数量、分类筛选、频道名称、来源层级、协议、分辨率、编码、节点延迟、最近 30 次可用率、评分、状态和最后检测时间，并提供四种订阅的直接链接及来源、权利和检测节点说明。

## 12. GitHub 自动化

`update.yml` 每天定时运行，也支持手动触发。工作流安装 Python 和 FFmpeg，先运行测试，再抓取、检测、生成和校验；只有生成文件变化时才自动提交。并发锁防止多个工作流同时写入。

`discover.yml` 每周运行，也支持手动触发。它在配置限制内搜索 GitHub，把新源加入隔离候选池，再通过相同流水线验证。

GitHub API 限流、来源超时和个别源失败属于可接受的部分失败，必须记录但不能清空现有输出。临近 Actions 总运行时间预算时停止调度新候选，完成已有结果校验，剩余候选顺延到下一次任务。

## 13. 异常处理与安全限制

- 为 DNS、连接超时、HTTP 状态、无效列表、分片缺失、无视频轨道、媒体超时、不支持协议和策略拒绝定义稳定失败代码。
- 限制重定向次数、响应字节数、列表嵌套深度、子进程时间和输出大小。
- 第一版只允许 HTTP/HTTPS；重定向地址和列表派生地址必须重新校验。
- 限制单域名并发和请求频率，避免给来源服务器造成压力。
- 日志不得输出令牌、Cookie、认证头或含敏感查询参数的完整 URL。
- 不保存视频或音频内容，也不提供 IPTV 中转服务。
- 外部文本在序列化前校验，并在网页显示时转义。

## 14. 测试策略

- 单元测试覆盖 M3U 解析、URL 标准化、去重、频道别名、分类、滚动历史、评分、主备切换、生命周期和 M3U/JSON 生成。
- 使用本地模拟 HTTP 服务测试重定向、超时、HTML 错误页、无效 HLS、主/媒体播放列表和可访问分片。
- 媒体复检测试使用受控的 `ffprobe` 输出或替身，常规测试不依赖公网源。
- 集成测试使用确定性输入验证候选源到发布文件的完整流水线。
- CI 必须先运行测试；测试或输出校验失败时禁止更新订阅。

## 15. 开发顺序

1. 建立 Python 包、配置结构、统一数据模型和测试夹具。
2. 实现 M3U 获取与解析、URL 标准化和去重。
3. 实现受限并发的异步 HTTP 初筛。
4. 实现受限并发的 `ffprobe` 媒体复检。
5. 实现频道白名单、别名和四个分类。
6. 实现 30 次滚动历史、评分、主备切换和生命周期清理。
7. 生成并校验四个 M3U 文件、状态 JSON 和报告 JSON。
8. 添加每日更新和每周发现 GitHub Actions 工作流。
9. 添加轻量 GitHub Pages 状态页。
10. 完成本地运行、GitHub 部署、维护和故障处理文档，并执行端到端验证。

每个阶段都必须产生可独立验证的行为。实现采用测试驱动方式，公网实际源检测与确定性单元测试相互分离。

## 16. 第一版明确不做

第一版不包含数据库或后端服务、用户端实时测速、多地区检测节点、自动中转或转码、RTMP/RTSP 发布、UDP/RTP/SRT、P2P 或专用插件、频道 Logo、市县级频道，以及任何需要认证或受保护的播放源。
