# 直连复核与首帧恢复

## 电视照片证明什么

用户TCL的1.0.3照片显示：CCTV-1，第1/3条74.91.26.218:82，PREPARING，首帧未出现、0已渲染帧、0×0、0ms缓存；恢复原因为first_frame_timeout，目录内容未变化。能说明目录已读取、该次没有可播放视频画面，尚不能只凭零缓存断言没有收到任何网络数据或电视解码器损坏。

GitHub Pages只提供频道目录，电视直接访问媒体上游；目录可读不代表上游可达。电脑已有FlClash隧道，之前通过电脑或模拟器的采样不能视为无代理实播验收。

## 物理网络结果

本轮通过Windows IP_UNICAST_IF指定WLAN接口、显式绑定本地IPv4，并直接向路由器进行UDP DNS查询；TCP、重定向和TLS均走同一接口，不关闭代理、不修改系统路由，TLS保留证书及SNI校验。此方式用于明确本次请求路径，不能把其他地区或运营商质量混为同一结果。

原264候选实际尝试169路径；新增公开列表42候选中实际尝试12路径。只有同主机发生网络连接失败时才跳过其余路径，不因403/404直接跳过整个主机。**实时直播直连合格0台。** 只有浙江三个入口可获取三完整分片并做1080P H.264/音频本地解码，但清单多分钟不变，节目日期是2025/2023年，因此是历史画面对照，不作为直播。

还检查了移动IPv6候选：本机WLAN有公网IPv6和物理默认路由；本轮两个公开候选主机分别返回403或连接超时，未尝试绕过限制。上述结果只涵盖本轮候选，不声称已经找遍所有公开来源。

独立直连报告在 `output/tv-direct-report.json`，`tv-direct.json`与M3U为明确的零合格证据，不替换客户端默认目录。旧试播中已剔除确认冻结的浙江入口，其余只保留为历史候选，不宣称在国内直连可用。

## 已修复代码

- 多源首次首帧/准备超时或首帧前明确连接失败，优先切下一条，避免在同条源上先等待重试和重建。冷却、隔离、耗尽终止仍有效；单源依然有限重试、重建后终止。
- 当前线路曾经出过首帧时，同源重试/重建保留成功标记，继续原有恢复预算；换源或选台才重置，避免重试阶段被误当作初次启动。
- 日志增加每次尝试读取字节、首个HTTP传输开始时间、累计等待和失败数；全部URL脱敏。HTTP传输开始不是TCP连接耗时或严格的网络首字节，0缓存也不再被当作0网络字节。
- 新增物理接口HTTPX适配器和DNS解析器：显式接口参数、DNS事务与问题校验、公网IP检查、连接/读取上限、TLS校验，不受HTTP代理环境变量或系统假IP解析影响。
- 试播检测必须复取媒体清单，验证最新节目时间、序号严格推进、新尾段和窗口顺序；只换签名、CDN主机、重排或冻结清单均不能视为直播。第二份清单再次做全部引用和密钥检查，避免更新后出现未检查私网地址。

## 验证与交付边界

Python全量185项通过；Android JVM38项、Android TV14项设备测试通过，含静默HTTP主源→离线可解码备源的有时限回归；构建与静态检查通过。受控测试只证明播放器能按预期切备，不能替代有真实上游的电视观看验收。
