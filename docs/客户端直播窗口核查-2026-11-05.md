# 客户端直播窗口核查

## 真实电视证据

已读取用户引用聊天及原始日志照片。1.0.3在CCTV-4、1.24.39.180:9003第二条线路上显示首帧2118ms，最终IDLE、0缓存，错误为ERROR_CODE_BEHIND_LIVE_WINDOW，异常链包含BehindLiveWindowException。因此已经连接并出过画面，不能继续归因为旧目录未更新或完全连接不上。

此错误证明播放位置落到当前直播窗口之外，不能单凭它认定是源、网络或播放器中的哪一方先造成落后。更新地址的频率与单条线路连续播放能力也不是同一件事。

## 已验证的客户端问题

1. 恢复策略耗尽后的EXHAUSTED会被后续STATE_IDLE覆盖，界面错误显示“待机”。设备回归在原实现实际失败，预期EXHAUSTED却得到IDLE；修复后保持终止状态及明确错误信息。
2. 原实现未区分直播窗口过期，会stop并重新setMediaItem，经过普通重试、重建才切备。它能重新创建媒体源，不能据此断言完全不会恢复；但属于过于粗糙的处理。现按Media3官方方法，在同一播放器、同一媒体项上seekToDefaultPosition与prepare，最多两次并有冷却和退避，失败后切备或终止，不无限prepare。
3. 普通BUFFERING/READY状态回调不直接调用prepare或创建播放器，受控重复回调测试通过。不能把“一秒一卡”直接说成一秒定时器在重建播放器；一秒定时器只检查健康条件，达到阈值才恢复。

新增状态回调与直播时间轴文件日志，记录恢复阶段、播放位置、缓存、直播窗口、live offset、清单序号、分片数和目标时长；不记录完整媒体URL或令牌。隐藏诊断页补充窗口和距直播点信息，仍无普通调试按钮。

## 验证边界

最终验证：Android JVM39项、电视模拟器17项设备回归全部通过，构建与静态检查通过。内置目录同步到用户要求的同源16个央视频道，避免安装后先从过期的旧快照启动；仅同步现有数据，未额外抓源。版本1.0.5，标准调试签名，可覆盖安装1.0.3。

新增受控设备测试：模拟错误时先使真实Media3播放器进入IDLE，再触发窗口过期回调，验证可再次出画、播放器对象不变、未重新setMediaItem；这是错误恢复路径验证，不是实际直播10分钟流畅度验收。

仅观察别的软件播放同名频道，或播放另一批M3U，不能替代同一地址、相同清晰度、相同设备与网络的连续对照。当前还不能确定周期性缓冲的全部起因，未盲目改20–45秒缓冲配置，未再大量抓源。

选源后续原则按用户要求：优先官方公开入口、国内CDN及国内网络实测线路；GitHub镜像只解决列表获取，不代表真正的媒体上游位于国内；新上传不等于稳定，不虚构未测记录。

官方依据：[Media3直播窗口与错误恢复](https://developer.android.com/media/media3/exoplayer/live-streaming#behindlivewindowexception-and-error_code_behind_live_window)。
